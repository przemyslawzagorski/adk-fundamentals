    Wzorce platformy — poza AuditOps¶

    Po co ta strona?

    Skills Pack, Audit Wiki i architektura progressive-disclosure powstały dla AuditOps (module_24), ale wzorce uogólniają się na dowolne narzędzie LLM w tym monorepo. Tutaj pokazujemy jak je przenieść.

    TL;DR — co da się ponownie wykorzystać?¶

    Wzorzec Gdzie powstał Gdzie pasuje
    Progressive disclosure (L1/L2/L3) module_24/skills_loader.py Każdy agent z ADK SkillToolset (module_14) lub surowym SDK LLM
    Wiki per-target (synteza z artefaktów) module_24/wiki.py Każde narzędzie produkujące JSON-y → module_13_code_analyst (wiki per-repo), module_22_spec_generator (wiki per-spec)
    Recon → aktywacja skilla (trigger deterministyczny) module_24/pentest_agent.py Każdy agent, który ma tani sygnał przed drogim planem
    DSL + dry-run + safety gates module_24/dsl.py, safety.py Każde narzędzie dotykające systemów zewnętrznych (Gmail w module_15, Postgres w module_09)
    MkDocs Material + Mermaid + i18n module_24/mkdocs.yml Całe repo — jeden punkt dokumentacji dla wszystkich modułów

    Wzorzec 1 — Progressive disclosure¶

    Trójka L1 manifest / L2 instrukcje / L3 referencje trzyma prompt mały, dopóki model nie wybierze ścieżki.

    # adk_training/module_24_audit_ops/skills_loader.py
def list_skills() -> list[dict]:
    """L1 — taniutkie. Zawsze wysyłaj. ~200 tokenów dla 5 skillsów."""

def load_skill(name: str) -> str:
    """L2 — ładuj tylko wybrany skill."""

def load_resource(name: str, rel_path: str) -> str:
    """L3 — referencje specjalistyczne na żądanie."""

    Jak przenieść do innego modułu¶

    1. Wrzuć skills/<nazwa>/SKILL.md obok narzędzia z frontmatter YAML: 
      ---
name: moj-skill
description: Krótki trigger w jednej linijce.
triggers: [slowo1, slowo2]
---
# Treść — instrukcje
    2. Wykorzystaj loader: 
      from adk_training.module_24_audit_ops.skills_loader import SkillsLoader
loader = SkillsLoader(skills_dir=pathlib.Path("module_X/skills"))
manifest = loader.list_skills()
    3. Wstrzyknij manifest do system prompt; pozwól modelowi zażądać load_skill(name).

    Wzorzec 2 — Wiki per-target¶

    wiki.py materializuje jeden katalog na target z index.md, findings/, scenarios/, skills/. Czysty markdown — operator może git diff, LLM może wciągnąć przy następnym uruchomieniu.

    artifacts/wiki/
└── example.com/
    ├── index.md
    ├── findings/A03-sqli-001.md
    ├── scenarios/login_flow.json
    └── skills/audit-history/SKILL.md   ← skill dynamiczny

    Gdzie jeszcze pasuje¶

    • module_13_code_analyst — wiki per repozytorium: findings/ to code-smells, scenarios/ to propozycje diffów.
    • module_22_spec_generator — wiki per spec: trzymaj różnice między rewizjami jako findings/spec-zmieniony-001.md.
    • module_20_analyst_system — wiki per ticket Jira: notatki śledcze + skrypty reproducera.

    Wzorzec 3 — Recon → aktywacja skilla¶

    Tani deterministyczny probe wybiera, które skille trafią do promptu:

    recon = http_probe(url)          # ~1 s, bez LLM
active = [s for s in all_skills if any(t in recon.signals for t in s.triggers)]
prompt = build_planner(active)   # tylko istotne skille

    To trzyma koszt tokenów stały niezależnie od liczby skillsów. Masz 50? W prompt i tak trafi 4-6.

    Narzędzie Tani probe Drogi plan
    AuditOps HTTP recon LLM synthesis scenariusza
    Code Analyst (m13) git log --stat + file count Propozycja refactoringu
    Spec Generator (m22) parse istniejącego OpenAPI Wygenerowany spec
    Database agent (m09) \d+ table_name Query plan reasoning

    Wzorzec 4 — MkDocs jako jeden dom dokumentacji¶

    Dziś mkdocs.yml żyje w module_24. Rekomendowana migracja:

    1. Przenieś mkdocs.yml do roota repo.
    2. Każdy moduł zachowuje swój folder docs/.
    3. Wykorzystaj mkdocs-monorepo-plugin.
    # /mkdocs.yml w roocie
nav:
  - Home: index.md
  - Moduły:
      - AuditOps (m24): '!include adk_training/module_24_audit_ops/docs/mkdocs.yml'
      - Concierge (m23): '!include adk_training/module_23_auggie_integration/docs/mkdocs.yml'

    Szacowany wysiłek: pół dnia na moduł, żeby wyciągnąć README → docs/.

    Macierz decyzji — przenosić czy nie?¶

    flowchart TD
    A[Nowe narzędzie / agent] --> B{Czy potrzebuje<br>planów wieloetapowych?}
    B -- Nie --> Z[Pomiń skille — pojedynczy prompt wystarczy]
    B -- Tak --> C{Czy plany się różnią<br>w zależności od inputu?}
    C -- Nie --> Y[Jeden duży prompt]
    C -- Tak --> D[Dodaj SKILL.md na każdą gałąź]
    D --> E{Czy generuje artefakty<br>warte zachowania?}
    E -- Tak --> F[Dodaj wiki per-target]
    E -- Nie --> G[Tylko skille — gotowe]
    F --> H{Czy użytkownicy<br>powrócą do tego samego targetu?}
    H -- Tak --> I[Dodaj dynamiczny skill audit-history]
    H -- Nie --> G
